# ADR-058: Naming Profiles are Parse-Only with Template-Driven Vocabulary

**Status:** Accepted
**Date:** 2026-06-02
**Deciders:** Brent (product owner)
**Supersedes:** [ADR-023](ADR-023-cro-naming-profiles.md) (Configurable CRO Naming Profiles)

## Context

bioAF's Naming Profile feature was built on the assumption that bioAF
should dictate the structure of uploaded filenames. The original design
shipped with:

- A closed enum of recognized "fields" hardcoded in
  `backend/app/schemas/naming_profile.py`:
  `date`, `project_code`, `experiment_code`, `sample_id`, `sample_index`,
  `data_type`, `analysis_type`, `researcher_initials`, `version`,
  `batch_id`, `organism`, `ignore`. Adding any new concept required a
  code change and a deploy.
- An intent (described in the original feature notes, though never
  shipped per a code audit) to **rename uploaded files** to conform to
  the profile.
- The presumption of a single "right" naming convention per
  organization.

Real-world usage exposed three failures of that model:

1. **bioAF does not own project / experiment / sample codes.** These are
   either generated by bioAF or pushed in from an external LIMS via API.
   Treating the filename as the authoritative source of those codes is
   backwards: the canonical record is the database row, and the
   filename is at best a hint.
2. **Biologists name files in their own conventions, and those
   conventions are unboundedly varied.** Read indices, batch numbers,
   instrument serials, operator initials, tissue types, lanes, re-scan
   counters, custom internal codes, sequencing run IDs: an open set.
   Any closed enum of "kinds of segment" is doomed to either reject
   real filenames or balloon over time as we chase additions.
3. **Different teams within one organization use different
   conventions.** A "the right naming convention" is the wrong unit;
   teams need to author their own.

Meanwhile, the Experiment Template feature
([backend/app/models/experiment_template.py](../../backend/app/models/experiment_template.py))
solves an adjacent problem: it lets users define arbitrary custom
fields (typed as `string`, `number`, or `date`) and reuse them across
experiments and samples. Naming Profiles and Experiment Templates are,
on inspection, two faces of the same idea: a team's vocabulary for
describing their work. They were built independently and the redundancy
is not paying for itself.

The glossary already flags Naming Profile as **volatile**, signaling
that an ADR codifying the intended direction is overdue.

## Decision

Reframe Naming Profiles around two principles:

### 1. Naming profiles are parse-only

bioAF reads information **from** filenames. It never renames, rewrites,
standardizes, or otherwise mutates filenames on upload or anywhere else.
The filename the user provides is the filename bioAF persists.

This is a hard contract, not a default. Any future feature that wants
to mutate filenames must do so under its own banner, not under the
Naming Profile feature.

### 2. Field vocabulary is sourced from Experiment Templates and is unbounded

A Naming Profile may optionally reference an Experiment Template. When
it does, the template's custom fields become the starting vocabulary of
fields the profile can extract. Users may also create fields ad-hoc
within the profile wizard, with an opt-in prompt to promote those
fields back to the template.

The only closed enum in the new schema is the three **field types**
(`string`, `number`, `date`), inherited verbatim from Experiment
Templates. There is no closed enum of **field names**. A user may
invent any field name they want, subject to basic validation.

Three system-managed codes (`ProjectCode`, `ExperimentCode`, `SampleID`)
appear in the wizard as pre-built "chips" because bioAF itself
generates those codes. They are the only hard-coded fields. Every other
field is user-defined.

### Segment shape

Segments encode their identity in the filename so order is irrelevant
at parse time:

- `number` -> `<1-4 letters><zero-padded integer>` (e.g. `SMP0042`).
- `string` -> `<1-4 letters><inner-separator><value>` (e.g.
  `req-bmills`). The inner separator is the opposite of the profile's
  delimiter.
- `date` -> one of three pre-built formats (`YYYYMMDD`, `YYYY-MM-DD`,
  `YYMMDD`), with no identifier; recognized by digit pattern.

Parsed values are returned as strings, except dates which are returned
as ISO date strings. Leading zeros are preserved (`SMP0042` parses to
`"0042"`, not `42`).

### Persistence rule for parsed values

If a parsed field has a matching custom field on the target experiment
or sample, the value is persisted to `experiment_custom_fields` as
normal (mechanism deferred to the auto-ingest rework). If a parsed
field has no matching custom field, the value is **human-readable
only**: it is reported by the parser and visible in any UI that shows
parser output, but it is not written to the experiment record. This
makes ad-hoc fields safe: profile authors can experiment without
silently polluting structured metadata.

## Consequences

### Positive

- Closed enums of field names disappear from the schema, code, and UI.
  New conventions never require a code change.
- Experiment Templates and Naming Profiles unify into one mental model
  ("a team's vocabulary"), reducing the surface users have to learn.
- File contents and filenames are decoupled from bioAF's internal
  naming. Teams keep their conventions intact.
- The "no rename" contract simplifies the upload path and removes a
  whole class of "why did bioAF change my filename" support questions.

### Negative

- Existing Naming Profiles do not migrate. Beta-feature users (one
  known: the product owner) re-author their profiles.
- Auto-ingest breaks during the transition. It is gated off and
  reworked in a follow-up. The naming-profile-to-experiment selection
  logic (which profile parses which file?) is open and will be
  designed in that follow-up.
- The wizard becomes more flexible and therefore more complex than
  the original "pick from a dropdown" flow. Mitigated by the
  template-picker shortcut and pre-built system chips.
- Profile authors can side-effect templates (by promoting ad-hoc
  fields). Mitigated by an explicit prompt at save time and the
  "human-readable only" persistence rule.

### Glossary impact

The existing `Naming Profile` entry in
[ai_guides/glossary.md](../../ai_guides/glossary.md) is rewritten;
new terms (`segment identifier`, `inner separator`, `system chip`) are
added. See [glossary-deltas.md](glossary-deltas.md) for the proposed
changes.

### Code impact

See [redesign-plan.md](redesign-plan.md) section 9 for the full schema
delta. Summary:

- Drop the closed enum in
  [backend/app/schemas/naming_profile.py](../../backend/app/schemas/naming_profile.py).
- Add `experiment_template_id` FK (nullable) and remove
  `project_code_mappings` / `experiment_code_mappings` from
  [backend/app/models/naming_profile.py](../../backend/app/models/naming_profile.py).
- Rewrite the parser at
  [backend/app/services/naming_profile_parser.py](../../backend/app/services/naming_profile_parser.py).
- Rewrite the wizard at
  [frontend/src/components/naming/NamingProfileWizard.tsx](../../frontend/src/components/naming/NamingProfileWizard.tsx).
- Gate auto-ingest behind a temporary "disabled during redesign"
  short-circuit. See
  [spec-auto-ingest-neutralize.md](spec-auto-ingest-neutralize.md).

## Alternatives considered

### A. Keep the closed enum and grow it

Add new entries to `SEGMENT_FIELDS` as biology teams request them.
Rejected: every new team eventually requests another addition, and
the cycle never converges. The enum becomes a backlog of requests
rather than a designed surface.

### B. Make naming profiles fully free-form (no identifier letters,
parse purely by position)

Rejected: position-based parsing is fragile (one extra segment in a
filename and everything shifts), and biologists routinely vary the
order of segments between batches. The identifier-letter scheme
trades a small amount of authoring effort for substantial parsing
robustness.

### C. Tie naming profiles to a separate "field library" entity,
not to Experiment Templates

A library of fields scoped to the org, reusable by both templates
and profiles. Rejected as over-engineered for the current need:
Experiment Templates already function as that library in practice,
and introducing a third entity adds concept count without solving
a concrete problem. Revisit if templates prove too coupled to the
"experiment" concept for shared use across other features.

### D. Continue to rename files on upload

The original intent. Rejected: see Context. Filenames are part of
the user's record-keeping, not bioAF's.

## Status notes

- Auto-ingest depends on this decision and will be reworked in a
  follow-up effort. The selection question (which profile parses
  which file?) is deferred to that work.
- A `freeze` flag on Experiment Templates (to disallow side-effect
  field additions through the profile wizard) is a plausible later
  addition; out of scope here.
